# Checkout and delivery-quote security review — 2026-10-29

## Scope and evidence

Read-only review of `checkout-v2.html`, `supabase/functions/store-checkout/index.ts`, and the committed source snapshot `supabase/migrations/20261013070000_create_store_order_v2.sql`. No live request was submitted and no production resource was changed.

## Confirmed critical gap

- The browser obtains delivery quotes from `/functions/v1/shipping-quote`, stores the selected quote in browser state, and sends it with checkout as `p_delivery_quote`.
- The public `store-checkout` Edge Function passes the browser-supplied quote payload through to `create_store_order_v2`.
- The SQL function checks only that `p_delivery_quote.live` is boolean true, that the payload price is non-negative, and that it matches the separately submitted delivery fee. These checks do **not** prove the quote was generated by the trusted server or that its price/provider/service/address/parcel are authentic.
- A client can potentially forge `{live:true, price:...}` and the matching `p_delivery_fee`. This means delivery-charge integrity is not established by the reviewed source. Treat delivery checkout as **NOT SECURITY-APPROVED** until fixed and tested.
- The repository's `supabase/functions` directory does not contain the referenced `shipping-quote` source, but read-only retrieval from the live Supabase project exposed deployed `shipping-quote` v4 and `store-checkout` v5. The quote producer obtains provider rates server-side and emits `live:true` for successful upstream responses; it does not issue a signed token or server-stored quote ID. The browser can still fabricate the same object shape and bypass that provenance check in checkout. Both functions currently have `verify_jwt=false`. Live function source was inspected read-only; no endpoint was invoked and no order was submitted.

## Required remediation (do not deploy until end-to-end reviewed)

Preferred design:
1. Make the delivery-quote endpoint produce a server-side quote record or cryptographically authenticated, short-lived quote token. Bind it to the exact destination/address, parcel dimensions/weight, cart SKU/quantities, provider/service, quoted amount/currency, and expiry.
2. At checkout, verify the quote record/token server-side, including signature, expiry, binding to the submitted address and cart, and that the selected amount is the recorded provider amount. Never trust a client-supplied `live` flag.
3. Ensure the SQL order RPC can only consume verified quote data from a trusted server path. Keep direct public execution revoked. Avoid a design where a public caller can self-assert quote validation.
4. Add negative tests for forged `live=true`, changed price/fee, changed address, changed cart/parcel, expired quote, replay/tampering, and quote from a different provider/service. Add a valid quote test and a free-pickup test.
5. Add abuse controls for the privileged checkout endpoint (input validation, rate limiting/idempotency where appropriate, safe error handling). CORS `*` is not authentication and must not be treated as a security control.
6. Test in non-production first. Only apply a reviewed migration and deploy functions after the owner explicitly approves the release and secrets/provider details are configured.

## Other launch status

- The reviewed order RPC accepts only `direct_eft`; payment stays pending. This is not evidence of a live PayFast or PayJustNow integration.
- Product price validation in the Edge Function and SQL rechecks the VAT-inclusive formula `cost_price * 1.15 * 1.35`; stock/price confirmation gates are present in the reviewed source.
- The RPC source snapshot grants execution to `service_role` only. Keep this restriction.
- No live database, Edge Function, product, stock, price, DNS, payment, or deployment changes were made during this review.
- Store launch remains **HOLD** pending the quote-integrity fix, non-production negative tests, payment readiness, and final launch checks.


## Follow-up source review — 2026-11-04
The 2026-10-29 finding above describes the earlier unsigned-quote implementation and is retained as historical evidence. A later source update is now present on `main`:

- `supabase/functions/shipping-quote/index.ts` creates short-lived HMAC-signed quote tokens using `DELIVERY_QUOTE_SIGNING_SECRET`. Claims include cart hash, destination hash, provider, service, amount, ZAR currency, parcel dimensions, issue/expiry timestamps and a nonce.
- `supabase/functions/store-checkout/index.ts` no longer treats browser-supplied `live=true` as proof. It verifies the token, expiry, cart/address/provider/service/price/currency/parcel binding and recomputes parcel dimensions from current product data before calling the service-role-only `create_store_order_v3` RPC.
- `supabase/functions/_shared/delivery-quote.ts` contains the HMAC verification and binding checks. `supabase/migrations/20261029150000_delivery_quote_nonce_unique.sql` adds a unique partial index on the stored quote nonce to prevent successful replay/concurrent reuse. `create_store_order_v3` remains revoked from PUBLIC/anon/authenticated and granted to service_role only.
- Tests are present: shared token/expiry/cart/address/parcel/pickup tests; checkout-handler integration tests for forged, tampered, expired/binding/fee and valid quote paths; and an isolated PostgreSQL nonce migration test. The `delivery-quote-security.yml` workflow runs these plus type checks and related privacy/WhatsApp tests.
- **Verification limit:** this was a read-only source inspection. No current successful workflow run or live deployed-function version was independently confirmed in this review. Therefore the original source-level weakness appears addressed in current `main`, but checkout is not signed off until the workflow passes on the exact release candidate and the same function/migration versions are verified in non-production. Production remains HOLD.
